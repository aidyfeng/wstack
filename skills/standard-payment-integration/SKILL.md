---

适用前提：

- 产品同时或将要接入多种支付通道（应用内购、移动端代扣、网页一次性下单等）
- 至少一种通道涉及自动续费订阅，需要区分"能代扣的渠道"与"只能一次性付款的渠道"

本篇的核心矛盾：**不同支付通道的能力差别巨大，不是"都能收钱"那么简单**。应用内购
（Apple IAP / Google Play）自带自动续费订阅、平台服务端通知、平台强制抽成，且**不允许
引导用户去站外支付**——这一条**全球一致**。

非内购渠道的能力分布则**因地域而异**：国内的典型形态是移动端 SDK 代扣能做自动续费但要走
签约流程、网页一次性下单多数只能做一次性支付（自动续费需额外商业资质，见⑧）；海外的
订阅型收单网页侧本身就能做订阅，没有这道割裂。**方法不变**——先把各通道的真实能力查清楚
再建模。把这些差异当成"细节以后再填"留到实现阶段才发现，代价是返工整条领域模型。

## ① 通道能力必须建模到领域层，不是揉进一个大 Protocol

**做法**：在套餐/商品的领域模型上标注「可售渠道」，依据是**支付通道的能力**，不是产品
想不想卖：

```python
@dataclass(frozen=True)
class PlanSpec:
    code: str
    price_cents: int
    period_days: int
    auto_renew: bool
    channels: frozenset[str]  # 可售渠道，按支付通道能力划分——不是按前端排期决定
```

自动续费套餐只在支持代扣/内购的渠道出现；网页一次性下单渠道只卖一次性买断。哪天网页
渠道的代扣资质批下来了，改这一行 `channels` 就能开放自动续费，不用碰任何业务逻辑——
能力判断收敛在一处，而不是散在各处 `if channel == "web": ...`。

下单/签约入口必须校验这一约束，防止绕过前端展示直接构造请求购买不可售渠道的套餐：

```python
if command.channel not in plan_spec.channels:
    raise PlanNotAvailableForChannelException(...)
```

**❌ 反模式：一个大 Protocol 强行覆盖所有通道**，靠"这个方法对某些通道无意义"的注释
兜底：

```python
class PaymentProvider(Protocol):
    async def initiate_sign(self, ...) -> SignInitiation: ...
    async def deduct(self, subscription) -> PaymentOrder | None: ...
        # 内购型：续费由平台自动扣款 + 异步通知驱动，此方法恒 no-op
    async def query_order(self, out_trade_no: str) -> dict | None: ...
        # 内购型：主动对账需要额外的平台 API 凭据，本期未接，恒 no-op
    async def unsign(self, subscription) -> bool: ...
        # 内购型：退订只能用户去系统设置操作，此方法恒 no-op 返回 True
    async def refund(self, subscription) -> bool: ...
        # 一次性下单型：本期未接自助退款 API，退款走人工流程，恒 raise
    async def handle_callback(self, raw_payload: dict) -> PaymentOrder | None: ...
        # 一次性下单型：回调走路由专属分支处理，不经过这个方法，恒 raise
```

**如实写这条的代价**：阅读者看到六个方法，不看每个实现连哪几个真正干活都判断不出来；
新增第三种通道时，不知道该把六个方法都实现一遍还是可以跳过大半——规范本身没给出判断
依据，只能翻已有 provider 的实现当参考。这不是"写得不好"，是**用统一接口套异构能力**
这个选择本身自带的代价，做这个决定时要清楚自己在换什么。

被标记 no-op 的方法，行为上要么显式 `raise NotImplementedError`（正常调用路径本就不该
触发它，触发即说明上游分流逻辑有 bug，应该失败可见）要么返回明确的"不适用"默认值——
**不要静默返回"成功"**，那会把"没做成"伪装成"做成了"。

## ② 幂等键因交易类型而异，同一模块里可能有两套相反的要求

这是最容易踩、后果最隐蔽的一条：**非续费型（一次性）内购每次购买分配的"原始交易 id"
都会变，不能拿它做幂等键；而自动续费型的它是稳定的、正是幂等键本身。**

```python
if plan_spec.auto_renew:
    # 自动续费：整个签约合同期内原始交易 id 恒定，可作幂等键直接反查
    sub = await subs.find_by_contract_id(original_transaction_id)
else:
    # 非续费：每次购买这个 id 都不同，find_by_contract_id 恒查不到——
    # 必须改按 (user_id, 商品编码) 反查该用户已有记录，做「叠加」而非「覆盖」
    sub = await subs.find_by_user_and_plan(user_id, plan_code)
```

幂等命中之后的自愈逻辑也要分流，不能共用一套：自动续费重复提交时可以拿本次交易的到期
时间去刷新（"只推进不回退"，正常重复提交不受影响，权益意外落后时还能自愈）；非续费的
到期时间是"叠加"算出来的，不是权威值，**如果照抄自动续费那套自愈逻辑，会拿单次交易的
到期时间去覆盖/推进已经叠加多次购买的结果——这是一个可以被反复提交同一笔交易刷权益的
安全漏洞**，非续费幂等命中时必须只读现状返回，不做任何写操作。

**结论**：接入前先确认"这个交易类型下，哪个字段是稳定的"，不要假设同一个平台的所有
交易类型幂等键一致。写代码时把两条路径显式分开，不要共用一个 `_is_duplicate()` /
一套通用幂等函数——它们的正确行为是相反的。

## ③ 订单号由调用方生成，不依赖 provider 回传

一次性下单型 provider 需要商户订单号，由应用层生成（ULID 之类）并**先落库**，再传给
provider 发起支付：

```python
out_trade_no = generate_ulid()
order = PaymentOrder(out_trade_no=out_trade_no, status="pending", ...)
await order_repo.save(order)                 # 先落库
redirect = await provider.initiate_sign(..., out_trade_no=out_trade_no)
```

这样在 provider 调用失败/超时时，本地仍有一条 pending 订单记录可查、可重试、可对账，
不会出现"钱可能扣了但系统里完全没有痕迹"的黑洞。代扣型/内购型 provider 不使用这个
参数——购买行为发生在客户端，没有"我方先生成商户单号再下单"这一步。

## ④ provider 不读 HTTP 请求

场景类信息（如按访问设备分流的支付页面形态）由路由层解析请求后**显式传参**给 use case
与 provider，provider 自身不碰 request 对象：

```python
PaymentScenario = Literal["pc", "wap"]   # 路由解析 UA 得出，显式传入，provider 不读 HTTP request

async def initiate_sign(self, ..., scenario: PaymentScenario | None = None) -> SignInitiation:
    ...
```

不这么做的代价：provider 会依赖一个只有在真实 HTTP 请求里才存在的上下文，无法单测直接
构造调用，也无法被后台任务/定时对账脚本复用（那些场景根本没有 HTTP 请求）。

---

## ⑤ 回调：先验签，再进业务

异步回调必须验签（含签名、金额、受众等全部字段）通过才进入业务逻辑；业务逻辑本身要
处理"同一笔通知被重复投递"这个常态，不能假设回调只会到达一次。

回调处理失败（验签不过、业务处理异常）要让平台重投——按平台约定返回非成功状态，而不是
吞掉异常回一个"成功"。吞掉等于告诉平台"我已经处理好了"，但其实没有，这笔通知永远不会
再来，钱收了权益却发不出去，且没有任何重试机会。

---

## ⑥ 对账要有主动查单能力

除被动回调外必须有 `query_order`——回调丢失不是小概率事件，而是网络抖动、部署窗口重启、
平台重试次数耗尽等原因下必然会发生的常态。没有主动查单，用户付了钱但权益没到，只能等
用户投诉后人工翻账。

**用"查会员/查权益状态"接口代替"查这一笔订单状态"是不成立的**：如果用户本来就已经是
会员，再叠加购买一单，查权益状态接口第一次轮询就会返回"是会员"，哪怕这笔新单根本没
到账——只有按订单号主动向支付平台核实这一笔的真实状态，才能确认这笔钱到底有没有走完
流程。

查单结果与回调共用同一套结算入口（同一个"标记已支付 + 发放权益"的用例），两条路径谁
先到达都只应该真正生效一次——结算入口自身要做到并发安全（例如"仅当订单仍是待支付状态
才转已支付"的原子更新），不能靠调用方各自判断"我要不要重复处理"。

## ⑦ 换账号 / 跨账号的权益归属

应用内购绑定的是**平台账号**（如 Apple ID），不是产品自己的用户账号。用户换一个应用
账号登录、又在同一台设备上点"恢复购买"，会出现"这笔订阅原本属于账号 A，现在账号 B 想
要"的冲突。

接入前想清楚并显式实现：验票/验通知时反查到该笔交易已绑定另一个应用账号，是直接拒绝
（不静默转移权益，防止后登录的账号顶替正在使用的付费用户）还是走人工客服核实转移？
不显式处理，默认行为往往是"静默转移给最后一次验票的账号"，那是一个可被利用的安全漏洞。

---

## ⑧ 选型：先查商业准入，再谈技术（这道门槛限中国大陆）

在中国大陆，自动续费能力（无论网页代扣还是移动端代扣）背后往往有硬性商业资质门槛——
注册资本规模、历史交易流水规模等，且各支付平台的门槛不互通。**这是业务问题，不是技术
问题**，技术方案设计得再完善也绕不过。

★ 海外没有这道门槛：主流订阅型收单开通账号即可做自动续费，本节整节可跳过。但下面那个
"先上一次性支付、把自动续费标注为待开启"的折中做法本身仍然有用——任何"能力暂时缺位"的
场景都适用，不限于资质原因。

选型阶段先确认资质能不能过，再决定要不要把自动续费排进技术方案；确认做不到时的常见
折中是**先上一次性支付，把自动续费依赖标注为"资质就绪后开启"**——领域模型（见①）已经
把"渠道可售能力"抽成了一个字段，资质到位后是配置变更，不是重新设计。
