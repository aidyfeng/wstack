适用前提：

- 工作流引擎面向 **LLM 对话场景**：节点类型包含 LLM 调用、知识库检索、意图识别等，执行
  路径可能因 LLM 输出/条件分支而动态变化，不是一张预先完全确定的固定流程图
- 需要给运营/开发者提供**调试能力**：单步触发一次执行，实时看到每个节点的输入输出与流式
  内容
- 图的**编辑**（画布、草稿/发布）与**执行**是分离的两个阶段——本篇只覆盖执行侧

不适用：图怎么画、怎么存、怎么发布不在本篇范围，那部分是通用的图编辑器规范，见

固定流程、不含 LLM 推理决策，那类场景数据流更简单，不需要变量表达式解析这套机制。

## 节点间数据流：共享 state + 模板变量引用

每个节点执行后，输出以 `dict` 形式存入共享执行状态：

```python
state["node_outputs"][node_id] = {"text": "...", "confidence": 0.9}
```

后续节点通过模板变量语法引用前驱节点的输出字段：

```
{{node_id.field}}
```

- **不支持嵌套引用**（如 `{{a.{{b.c}}}}`）——解析器按简单正则单趟扫描，故意不支持嵌套是为
  了让解析保持无状态：嵌套需要递归解析和循环引用检测，复杂度上升但多数场景一层引用就够用
- 提供一个**特殊变量**指向用户原始输入（如 `{{start.user_input}}`），让"用户输入"也走统一
  的变量引用语法，不需要在模板语法里单独开一套规则

✅ 每种节点类型的输出字段用**约定俗成的标准命名**，跨节点类型尽量统一（如都用 `text` 表示
主要文本输出），减少下游模板作者的记忆负担
❌ 每个节点类型输出字段命名各自为政（有的叫 `text`，有的叫 `content`，有的叫 `output`）——
模板作者需要为每种节点类型单独记字段名，错误率高且难排查：字段名写错不会报错，只是解析出
空值，问题要等结果核对时才被发现

## 变量解析失败：必须显式报错，不能静默吞掉

- **引用未执行节点必须抛异常，不能返回空字符串/`None` 悄悄放过**——静默返回空值会让下游节点
  拿着一个"看起来正常、实际是空"的输入继续跑，产出内容里少一块，但整条链路不报错、日志也
  正常，只有人工核对结果时才会发现，而且难定位是哪个变量引用出的错
- **节点正常执行完但字段值恰好是 `None`**，与"引用未执行的节点"是两种不同情况，不能混为
  一谈：前者解析为空字符串是合理行为，后者多半是图设计错误（比如条件分支导致该节点被跳过），
  必须报错而不是一起被"空值兜底"盖过去
- 非字符串值（数字、bool、dict）解析进模板时统一 `str()` 转换，模板作者不需要关心类型

三个解析职责要分开，不要合并成一个大而全的函数：

| 职责 | 用途 |
|---|---|
| 解析单个表达式 | 给定 `{{node_id.field}}`，返回具体值 |
| 解析整个模板 | 模板里混着普通文本和多个变量引用，逐个替换 |
| 提取变量引用列表（不解析） | 只列出模板依赖哪些节点，用于图发布前的静态依赖分析 |

第三个职责的意义在于：图发布前可以**静态检查**"这个节点引用的变量，其来源节点在拓扑上是否
真的先于它执行"，而不用等运行时才报错。

## 新增节点执行器：完整步骤 + 多处注册陷阱

新增一种节点类型不是写一个执行器类就完事，是一条**多文件改动链**，漏一环会**静默失效**——
不报错，只是这个节点类型的某个能力悄悄不生效：

1. **值对象**——节点类型枚举新增一个值
2. **配置类**——`@dataclass(frozen=True)`，必须实现 `from_dict()` 和 `validate() -> list[str]`
3. **执行器**——继承基类，实现 `async execute(*, node_id, node_config, state, writer, **kwargs) -> dict`
4. **注册**——**在所有构建执行器注册表的地方都要注册**。如果调试执行和正式执行走两条不同
   的服务/代码路径，两处都要改；只改一处的后果是：调试时这个新节点类型能跑，正式发布执行时
   直接查不到执行器，或反过来
5. **图校验器白名单**——新节点类型要加进"合法节点类型"检查，否则图校验阶段就把这种节点判为
   非法，永远发布不了
6. **图校验器的配置校验分支**——新节点类型的配置字段校验逻辑要单独接进校验流程，否则配置
   填错了也不会在发布前被拦下来，等运行时才炸

❌ 最常见的漏项：只在"调试执行"服务里注册了新执行器，忘了"正式执行"服务那一份注册表——本地
调试全部正常，一发布到线上跑真实流量就找不到执行器，报错信息往往是"未知节点类型"，排查者
第一反应是怀疑发布流程出了问题，实际是代码里漏注册

✅ 把"新增节点类型"写成一份检查清单（本节六步），每次加新类型逐项打勾，比指望记住"哪些地方
需要改"更可靠

## 条件路由节点：必须返回可判别的分支标识

需要驱动图分支走向的节点（条件判断、意图识别），执行结果里**必须**包含一个专门字段标识
"走了哪条分支"：

```python
return {"matched_branch": "yes", ...其他字段}
```

- 编译器/引擎读这个字段决定下一步执行哪个后继节点
- **忘记返回这个字段，图会在这个节点后卡死或走向默认分支**——不报错，因为节点本身执行成功
  了（返回了合法的 dict），只是路由逻辑找不到该走哪条边，多数实现会默默 fallback 到某个默认
  分支或直接中断，两种情况都不会抛异常

✅ 新增条件类节点的执行器时，`execute()` 返回值的测试用例里显式断言可判别分支字段存在，
作为这类节点执行器的通用验收标准，而不是等图跑起来才发现分支不生效

## SSE 流式调试：事件生命周期与画布联动

调试是"发一条消息，实时看工作流怎么跑"的能力，通过 SSE 流式事件驱动：

```
workflow_start
  → node_start    (node_id, node_type, label)
  → node_input    (input)
  → node_stream   (content chunks, LLM 流式输出片段)
  → node_complete (output, duration_ms)
  或 node_error   (error, error_code, error_type)
workflow_complete
```

流结束要有**显式结束标记**（如 `[DONE]`），不能指望前端靠连接关闭来判断结束——连接关闭也
可能是网络异常，两种情况必须能区分。

**调试期间画布必须锁定禁止编辑。** 调试运行的是当前图的一个执行快照，如果调试过程中用户还能
拖节点、改连线，节点执行状态事件里的 `node_id` 会跟画布上已经变化的图对不上，界面会展示一个
和实际执行对不上号的状态。

**节点状态驱动画布可视化**：维护一个 `node_id → 状态` 的 map，状态机是
`pending → running → completed / error`。调试开始时全部节点重置为 `pending`，收到
`node_start` 改 `running`，收到终态事件（`node_complete`/`node_error`）改终态。画布组件订阅
这个 map，用状态驱动节点的视觉样式（如描边颜色），实现"边跑边看哪个节点在执行"的效果。

**SSE 客户端实现要点：**

- 用 `fetch` + `ReadableStream`（不是 `EventSource`）——需要自定义 header（如认证信息）时
  `EventSource` 原生不支持，只能手动读流
- 用 `AbortController` 支持用户主动取消调试
- 按行解析 `data: ` 前缀的 JSON，**要维护一个 buffer 处理跨 chunk 被截断的行**——网络层的
  chunk 边界和 SSE 消息边界不是一回事，一条消息可能被拆进两个 TCP chunk，一个 chunk 也可能
  装了好几条消息：

```typescript
buffer += decoder.decode(value, { stream: true });
const lines = buffer.split("\n");
buffer = lines.pop() || "";   // 最后一行可能不完整，留到下次 chunk 再拼
```

❌ 不维护 buffer，每个 chunk 到达就直接按行 split 处理——被截断的半行 JSON 解析失败，且这种
失败只在消息长度恰好跨 chunk 边界时出现，本地测试大概率遇不到，线上偶发难复现
