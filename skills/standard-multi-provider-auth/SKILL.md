适用前提：

- ★★ **面向中国大陆的产品**。⑥⑦⑧ 三节建立在两个只有国内才成立的前提上：手机号是事实上

- 已有一套统一的会话签发机制（cookie/token），本篇只解决"从各家 provider 换回统一的用户

- 至少接入两种登录方式（否则用不上下面的抽象，直接写一个专用流程更简单）

## ① 统一抽象的形状

各家 provider 返回的原始数据长得完全不一样（OAuth 的 `openid`/`unionid`、Apple 的
`sub`/`email_relay`、短信的手机号），但登录主流程只关心三件事：这是谁、联系方式是什么、
剩下的原始字段要不要保留。所以：

- 一个统一的 `ProviderUserInfo`：`provider` + `provider_user_id`（核心，见下一节）+
  冗余的 `email`/`phone`（便于按邮箱/手机号查重）+ `metadata`（JSONB，装各家专有字段，
  不为每个字段单独建列）
- provider 接口（Protocol）**只需一个 `authenticate(primary, secondary)`**，用两个
  泛化参数容纳完全不同的凭据形态——OAuth 是 `code`+`state`、短信是 `phone`+`otp`、
  Apple 是 `identity_token`+`nonce`。不要为每家开一个方法签名（`authenticate_wechat`/
  `authenticate_apple`……），那样登录主流程就没法对 provider 做统一分发，一新增一家就要
  改一次主流程
- 登录用例依赖 `dict[str, Provider]` 注入，**不直接 import 任何具体实现**——新增一家
  只是往这个字典里多注册一项，主流程代码零改动
- 可选基类只用来减少子类样板代码（统一存放 `name`、统一日志、把第三方 SDK 异常包装成
  领域异常）；Protocol 是结构化子类型，实现类**不必**继承它

策略模式本身（Protocol 定义、`I` 前缀、结构化子类型不需要显式继承）见
`standard-fastapi-ddd-backend` 的「模块分层」一节，本篇不重复展开。

## ② ★★ provider_user_id 的选择是不可逆决策

这是本篇最重要的一条：**必须选各平台"跨应用稳定"的那个标识，而不是随手能拿到的那个**。

- **微信**：必须用 **unionid**，不能用 openid——openid 是 per-app 的，同一个人在你的不同
  应用（App / 公众号 / 小程序）下 openid 各不相同；只有同一个开放平台账号下的 unionid
  才跨应用稳定
- **Apple / Google**：用 id_token 里的 `sub`（不是 email——邮箱可以换绑，`sub` 不会变）
- **手机号**：先规范化成 E.164 再存，同一个号码不同格式（带不带国家码、带不带前导 0）
  必须落成同一个值，否则查重形同虚设

**为什么不可逆**：选错了，同一个人在不同端会被系统认成不同用户；更麻烦的是**事后无法
自动修复**——openid 推不出 unionid，已经产生的账号数据没法程序化合并，只能让用户手工
申诉、人工核对身份后手动改库。这个决定必须在写第一行代码之前定死，不要等接入完成、
积累了真实数据之后再回头改标识选取逻辑。

## ③ 账号模型：一个用户多个认证账号

用一张**关联表**（user ↔ provider 账号，`(provider, provider_user_id)` 唯一），而不是
在 users 表上逐家加列（`wechat_openid`、`apple_sub`、`google_sub`……）：

- 加列的方式每接一家新 provider 就要改一次 users 表结构、改一遍查询逻辑，且**表达不了
  "同一个人绑了两个微信账号"这类多对一场景**
- 关联表天然支持"一个用户挂多个 provider 账号"，新增一家 provider 是纯数据操作，不动
  表结构
- 该表除了唯一约束还应支持**软删除感知的部分唯一索引**（`deleted_at IS NULL` 时才生效
  唯一），否则账号软删除后同一个第三方身份永远无法重新绑定

---

## ④ 登录主流程的分支

核心判据只有一个：`find_by_provider(provider, provider_user_id)` 命中与否。

- **命中** → 这是"跨设备/跨端登录已有用户"，取出该用户校验状态（是否被封禁/软删除）后
  直接签发会话，**不修改**已有账号资料（除非用来补全缺失字段，见下一条）
- **未命中** → 这是"新用户"，需要：新建 user + 新建 provider 账号记录（写入完整
  `metadata`），**这两步必须在同一个事务里**——分两步提交的话，中间进程崩溃会留下一个
  没有任何登录方式能访问的孤儿 user

**并发首次登录的竞态**：两个请求几乎同时用同一个 provider 身份首次登录（同一账号双端
同时打开、或客户端重试），都会 `find_by_provider` 落空后各自尝试建号，其中一个会撞
`(provider, provider_user_id)` 唯一约束。正确处理方式是捕获这个唯一约束冲突、删除本次
请求刚创建的孤儿 user、回查刚才撞车的那条账号记录，把本次请求收敛成对并发赢家的一次
幂等登录——而不是让异常直接冒泡成 500。

**已注册账号资料只补空缺、不覆盖**：命中已有用户时，若 provider 返回了昵称/头像而用户
当前该字段为空，可以补上；但用户若已经自己设置过，**不要用 provider 返回值覆盖**——
否则一次跨端登录就会悄悄改掉用户自己填的资料。

## ⑤ 绑定 vs 登录是两个不同的用例

"用一个新 provider 登录（找到/创建账号）"和"给已登录用户追加绑定一个新 provider"是两条
不同的流程，**不要合并成一个用例**：

| | 登录 | 绑定 |
|---|---|---|
| 前提 | 未登录 | 已登录 |
| provider 身份已存在于系统 | 直接登录该身份对应的用户 | 报错——"这个第三方账号已经绑给
别人了"，不能把当前登录用户的数据挪过去 |
| provider 身份不存在 | 新建用户 | 挂到当前登录用户 |

失败语义完全不同：登录流程里"provider 身份已存在"是正常分支（跨端登录）；绑定流程里
"provider 身份已存在"是异常分支（这个第三方账号已经被别的用户占用，必须拒绝，否则会把
两个人的账号数据错误关联到一起）。用一个 use case 兼两用会让这两种"已存在"的处理逻辑
互相干扰。

**跨账号合并场景**（例如"先用手机号注册过，之后才用第三方账号登录"想合并成同一个人）
本质上也是一种绑定：以某个已验证的强身份（如手机号 OTP）作为合并凭证，而不是仅凭
"两次登录声称是同一个人"就自动合并——自动合并会被用来窃取他人账号。

## ⑥ ★★ 手机号是唯一主身份，社交登录必须补绑（限中国大陆）

社交平台返回的身份只在该平台内可信。**定死一条：所有登录方式最终都要归到一个已验证的
手机号**——社交首次登录未命中 provider 时**不建号**，先补绑手机号，再连同 provider 身份
一起建号。

不这么做的代价，比"注册漏斗多一道墙"严重得多：

- **账号找回没有着落**。社交账号被封、用户换了 Apple ID、微信那边解绑了手机号——这些都
  不在你的控制范围内，而此时用户无法自证身份，客服也无从核对
- **同一个人分裂成多个账号**。先用手机号注册、后用社交账号登录（或反过来），两条路各建
  一个账号，会员权益与历史数据互不相通。这个分裂和②一样**事后无法自动合并**

代价如实记账：注册多一步；一键取号按次计费。**但不要用"一半 provider 强制、一半不强制"
来摊薄它**——规则不一致会让用户困惑"为什么这次要绑、上次不用"，也让接手的人分不清这是
bug 还是设计。

**不给跳过按钮**。给了跳过就等于回到不强制，只是多了一堵假墙。若某个分发平台的审核规则
逼你提供跳过（例如对"非必要信息收集"的限制），那是被迫降级，应作为已知偏离记录在案，
而不是预先妥协。

## ⑦ 号码验证是一个共用组件：两个入口，两条通道（限中国大陆）

**两个入口**——"验证这个手机号属于当前这个人"在两处是同一件事，不要实现两遍：

| 入口 | 起点 | 验证通过后 |
|---|---|---|
| 手机号登录 | 未登录 | 按手机号查：命中即登录，未命中建号 |
| 社交登录补绑 | 已拿到 provider 身份、尚未建号 | 建号并挂上该 provider 身份 |

**两条通道**——产出都是"一个已验证的 E.164 手机号"，对下游完全等价：

- **运营商一键取号**：客户端 SDK 取 token，服务端拿 token 换
  真实号码。运营商已经验证过号码归属，**等价于 OTP 已通过，不要再要用户输一次验证码**
- **短信 OTP**：兜底通道

★★ **两条通道必须落到同一个 provider 身份**。一键取号和短信 OTP 在账号体系里是同一家——
同一个 `(provider=手机号那家, provider_user_id=E.164 号码)`，不是两个 provider。给一键取号
单开一个身份标识，同一个人用一键登录和用短信登录就会分裂成两个账号，⑥要防的问题从内部
又发生一次。落地上：一键取号**可以**在 provider 注册表里占一个独立 key（它的凭据形态与
OTP 不同，分发逻辑需要区分），但它产出的用户信息里那个 `provider` 字段必须写死成手机号
那一家。这两件事是分开的，别混为一谈。

★★ **短信通道必须始终可达，且绝不能被当成"取消"**。一键取号有三类硬失败，全部只能靠
短信兜住：

- 必须有蜂窝数据。纯 WiFi、无 SIM 卡、平板 WiFi 版一律取号失败
- 双卡设备取到的是**默认数据卡**的号，未必是用户想用的那个
- 部分虚商号段不支持

★★ **授权页有三个出口，语义互不相同，必须分开处理**：

| 出口 | 用户的意思 | 该落到哪 |
|---|---|---|
| 「用短信验证」 | 还是这个号码，只是换个验证方式 | 留在当前流程，切短信表单 |
| 「换其他登录方式」 | 不用手机号了 | 回登录方式选择页，让他挑别的 provider |
| 返回 / 取消 | 放弃 | 回上一步，不报错、不提示 |

合并其中任意两个，用户就会"点了 A 却发生 B"。最典型的是把「返回」并进「切短信表单」——
用户点了返回，却发现自己还在绑定页，只是换了个样子。

★ **第一个出口通常要自己加**：SDK 自带的只有后两个，"还是这个号、只是换验证方式"这层语义
厂商没做。多数 SDK 支持往授权页塞自定义控件，加一个按钮即可。少了它，一机多卡的用户就
没有正路可走——他要的是换个号码验证，而不是放弃手机号登录。

★ **可用性探测失败要静默隐藏一键入口、直接展示短信表单**，不要留一个点了必然失败的按钮。
凭据未配置（如 CI 漏注入密钥）走同一条路——表现是"少一个入口"，而不是"多一个死按钮"。

一键取号的**接入细节**——SDK 只能从厂商控制台下载、码值与授权页定制 API 两端完全不通用、
iOS framework 往往不是 modular、回调 listener 会多次触发——见
`references/one-tap-number-auth.md`。那份是通用接入知识，换个项目再接一次同样适用。

## ⑧ 从"不强制"改成"强制"，有三个各自独立的陷阱（限中国大陆）

这三条只在**产品决策反转**时出现（原本社交登录不绑手机号，后来要求绑）。共同点是：
只改首次登录那个分支，全都盖不住。若把"手机号"换成别的强制身份（海外场景下的邮箱等），
三条同样成立。

★★ **存量账号绕过整条新逻辑**。已经建好的社交账号下次登录会**命中 provider 直接登录**，
压根走不到"未命中 → 补绑"那个分支。漏了它，新规则只对新用户生效，存量用户永远停在老状态。

拦截要做在**后端登录端点**里：命中 provider、但该用户名下没有手机号身份时，**不签发会话**，
直接返回"需要绑定"，与首次登录未命中汇流到同一条路。★★ 只做前端闸门是拦不住的——先把
会话 cookie 种下去、再引导用户去绑定页，用户关掉引导、手工改地址栏就绕过去了，而此时他
手上已经有一个完全有效的会话。这条是真机实测才暴露的，代码审查看不出来。

前端侧的补绑跳转放在**登录成功的收尾**里，做成一次性动作。★★ **不要做成包住路由树的持续
态闸门**：判据"已登录 && 未绑手机号"是一个持续为真的状态，做成闸门后，已经登录的用户每次
冷启动、每次切页都会被重新弹去绑定页，绑不完。这个方案上线过，然后被拆掉了。

★★ **闸门依据的字段必须真查库，不能吃默认值**。用户信息里那个"是否已绑手机号"的字段，
在手机号系端点上恒为真是对的，但**社交登录命中已有账号的分支必须真查**——存量账号正是
"命中 provider 但没有手机号"这一类。吃默认真值会让闸门在整个会话里静默失效，要等下次
刷新用户信息才纠正。这条错了不报任何错，只是静默放人进去。

前端按**三态**处理该字段：`true` 放行、`false` 拦截、`undefined` 放行。`undefined` 意味着
后端还没部署这个字段，此时**宁可漏拦、不可挡死**——挡死会让未升级的环境整个登不进去。

★★ **补绑撞上已被占用的手机号，要分三支，且判定顺序不能错**：

| 情况 | 处理 |
|---|---|
| 手机号未被占用 | 直接挂到当前账号（绝大多数） |
| 已属另一账号，**当前账号无付费** | 返回专用错误码要求二次确认；确认后**转绑**——provider 身份改挂到目标账号、当前账号软删、重签目标账号的会话 |
| 已属另一账号，**当前账号有付费** | 阻断，不自动处理，转人工 |

★ **付费判定必须排在"是否已二次确认"之前**。顺序反了，前端只要带上已确认标记就能绕过
这道安全阀。

★ **转绑前先校验目标账号可用**（未封禁、未软删）。这是不可逆的账号操作，正确性不能押在
"异常必然整体回滚"上——中间一旦插入一次提交，失败就留下"provider 身份已改挂 + 原账号已
软删 + 会话没签出"的残局，两个账号都登不进去，用户无法自助恢复。

★ 转绑要不要迁移业务数据是产品取舍，**必须写下来**。不迁移通常是对的（涉及多张业务表和
多个 `(user_id, X)` 唯一约束），但它要是一个记录在案的决定，不是一处遗漏。

---

## ⑨ 凭据校验的安全要求

不同 provider 换取到的凭据必须按各自协议正确校验，否则统一抽象反而会把校验疏漏放大到
所有接入的 provider 上：OAuth 类必须走 server-to-server 换 token（客户端凭据只能是
一次性 `code`）；JWT 类（Apple/Google 的 id_token）验签之外必须校验 `audience` +
`issuer` + `exp`，缺一不可。完整规则见 `standard-api-security-baseline` 的
「第三方身份验证」一节，本篇不重复。
