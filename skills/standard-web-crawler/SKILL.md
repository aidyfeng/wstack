## URL 标准化：先统一形态，再谈去重

同一个页面常有多种写法，不做标准化，"是否已抓取"的判断全部失真：

```
https://Example.com/a/b/                     （末尾斜杠 + 域名大写）
https://example.com/a/b#section2              （fragment）
https://example.com/a/b?utm_source=x&gclid=y   （追踪参数）
```

以上三个如果直接按字符串比较，会被当成 3 个不同 URL，同一页面重复抓取 3 次。标准化规则：

- scheme、netloc（域名）统一小写
- 移除 fragment（`#` 及之后内容）——同页面内的锚点跳转不是新页面
- 移除尾部斜杠（根路径 `/` 除外）
- 移除追踪参数（`utm_*`、`fbclid`、`gclid` 等）——这些参数不影响页面内容，只是营销归因用的

✅ URL 进入去重集合（`set` 或已抓取记录表）前先标准化，再比较
❌ 用原始 URL 字符串直接比较——同一页面因大小写、尾斜杠、追踪参数不同被反复当成新页面抓取，
浪费抓取配额，也可能因请求量异常触发目标站点的限流/封禁

## 抓取边界：同域、深度、页数三道闸

不设边界的爬虫在实践中几乎必然失控——网页互相链接，理论可达页面是无限的：

| 边界 | 作用 |
|---|---|
| **同域检查** | 只抓取与起始 URL 同域名的链接，避免顺着外链爬出整个互联网 |
| **最大深度** | 限制从起始页出发的跳转层数，建议设一个硬顶（如 10）防止误配置成极大值 |
| **最大页数** | 限制单次抓取任务的总页面数，同样要有硬顶 |
| **include/exclude 正则** | 精确控制抓哪些路径，如只抓某个子目录下的页面 |

URL 过滤顺序建议：**协议检查**（只允许 http/https，排除 `javascript:` `mailto:` `tel:`
`data:` 等伪协议）→ **同域检查** → **静态资源排除**（`.css` `.js` `.png` `.pdf` `.mp3` 等
一律跳过，这些不是"内容页"）→ **include 正则** → **exclude 正则**。

顺序本身有意义：先做便宜的检查（协议、域名字符串比较）过滤掉大部分噪音，再做相对贵的正则
匹配，减少无效计算——尤其在页数上限很大的任务里，这个顺序差异会累积成明显的性能差距。

## robots.txt 合规与限速礼貌性

- **抓取前检查 robots.txt**（`User-agent: *` 规则），不允许抓取的路径直接跳过，不是"抓了
  再看要不要用"——尊重目标站点声明的抓取边界，也是避免被封禁 IP 的前提
- **按域名缓存 robots.txt 解析结果**，不要每抓一个页面都重新请求一次——徒增对方服务器压力，
  也拖慢自己的抓取速度
- **robots.txt 本身不可用时（404/超时），降级为允许抓取**——不能因为拿不到 robots.txt 就
  整体放弃任务，多数站点根本没有配置 robots.txt
- **请求间隔限速**，且要可配置到接近 0（供内部/自己有权限的站点使用），但**默认值要保守**——
  高频无间隔抓取对小站点可能造成实质性负载，也是最容易触发目标站点 WAF 封禁的行为特征

❌ 不检查 robots.txt、不限速直接并发抓——短期内抓得快，但极容易被目标站点识别为攻击流量
封禁 IP，导致整个任务失败，得不偿失

## 失败重试与永久失败的区分

抓取失败分两类，处理方式完全不同：

- **临时性失败**（网络超时、5xx、限流响应 429）：值得重试，但要有**指数退避**和**重试次数
  上限**——无限重试会在目标站点持续故障时把自己的抓取任务也一起拖死
- **永久性失败**（404、403、DNS 解析失败、robots.txt 明确禁止）：**不值得重试**——404 不会
  因为多请求几次变成 200，重试只是浪费配额和时间

✅ 记录失败原因并分类：临时失败进重试队列（带退避），永久失败直接标记跳过并记录原因，供
后续排查"为什么这个页面没抓到"
❌ 所有失败走同一套重试逻辑——对 404 也重试是纯粹的浪费；反过来遇到任何失败都直接放弃不重试，
会把本该成功的临时网络抖动也计为抓取失败，抓取完整率莫名偏低

## 内容抽取：先剔除噪音，再谈"正文"

网页 HTML 里大部分标签不是正文内容，抽取前先排除：

```python
excluded_tags = ["script", "style", "nav", "footer", "header",
                 "aside", "form", "noscript", "iframe", "svg", "canvas"]
excluded_selectors = ["ads", "advertisement", "tracker", "cookie-banner", "popup"]
```

- 输出统一转成 **Markdown**（保留标题层级），比纯文本保留更多结构信息，比原始 HTML 更适合
  后续处理（如喂给下游流水线）
- **正文长度阈值别按西文分词方式设**——按空格分词计数的字数阈值对中文页面不准确（中文没有
  空格分词），会把正常长度的中文正文误判为"内容太短、疑似噪音"而丢弃。改用字符数统计，或
  阈值直接设为 0、把"是否噪音"交给标签/选择器排除去处理
- 排除外部链接和社交媒体分享链接、移除 overlay/弹窗类元素——这些是页面装饰，不是内容

## 增量抓取的变更检测

对同一批 URL 定期重新抓取时，全量重抓 + 全量重新处理下游流水线成本很高，值得先判断"内容是否
变化"：

- **简单方案**：对抽取出的正文内容算哈希（如 `sha256`），与上次抓取存的哈希比较，相同则跳过
  后续处理（不重新入库、不重新触发下游）
- **更省流量的方案**：先发 `HEAD` 请求，或带 `If-Modified-Since` / `If-None-Match` 的条件
  请求，服务端支持的话直接拿 304，连正文都不用下载
- **哈希前要先排除噪音源**：时间戳、随机广告位、访问计数器这类"设计上内容没变但每次渲染都不
  同"的片段，如果混进哈希计算，每次都会判定为"变了"，增量检测形同虚设——排除口径要和"内容
  抽取"节的噪音排除保持一致，两处不同步会让哈希基于不同的抽取结果，比较毫无意义
