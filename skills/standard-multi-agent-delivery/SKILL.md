# 多 Agent 协同交付

本规范定义总控 Agent 拆分任务、隔离开发、分层路由模型、执行双层审查与合入的通用做法。触发时机与流程入口见 [orchestration playbook](../wayne-mode/playbooks/orchestration.md)；验证证据与提交评审分级分别衔接 [standard-quality-gates](../standard-quality-gates/SKILL.md) 和 [standard-dev-workflow](../standard-dev-workflow/SKILL.md)。

## 拆分规则

按用户或外部调用方能直接观察到的端到端行为切分垂直切片，不按技术层横切。

| 做法 | 例子 | 结果 |
| --- | --- | --- |
| 垂直切片（采用） | 每个子任务交付一条可操作、可观测的完整路径或能力闭环 | 单个切片即可端到端验真，合入冲突少 |
| 技术层横切（禁止） | 把一条用户路径拆成「数据模型 / 服务层 / 接口 / 前端页面 / 单测」五个并行任务 | 碎片各自通过但主流程跑不通，联调和返工成本高 |

拆分必须满足四条约束：

1. **可见结果判据。** 每个子任务在派发前必须能写清「谁触发、执行什么操作、观察到什么结果」。写不出来说明拆得太细，必须合并回上层切片。
2. **耦合即合并。** 两个子任务只有拼在一起才能跑通一条用户路径时，属于强耦合工作，交给同一个实现 owner，不强拆并行。
3. **前置底座例外。** 仅当多个垂直切片共享同一份接口契约、核心数据模型或基础设施且并行写会直接冲突时，才抽一个最小前置底座切片（Wave 1）。底座切片必须自带静态与契约校验，并由紧随其后的垂直切片真实消费。
4. **文件所有权。** 派发前锁定共享契约与各切片可写目录边界；公共入口文件（路由注册、总出口、版本文件、迁移头）指定单一负责人或留到集成阶段统一收口。

## Worktree 拓扑

派发前先检查 `git branch`、`git status` 与任务耦合度，选定拓扑后再开子任务，不假设总是从默认主干出发。

| 当前状态与目标 | 拓扑模式 | 隔离与合入方式 |
| --- | --- | --- |
| 位于默认主干，多个垂直切片独立且各自提 PR | **主干扇出（Trunk Fan-out）** | 各切片从主干切独立 worktree，审查通过后各自提向主干的 PR |
| 位于自建特性分支 / worktree，最终合并为这一个 PR | **分支内回流（Feature Fan-in）** | 先将未提交改动提交为 checkpoint commit；各切片从当前 `HEAD` 切独立 worktree；初审与对抗审查以 `checkpoint..subtask-head` 为范围；通过后回流合入当前特性分支，统一跑集成验证再提 PR |
| 位于自建特性分支，当前分支已够大准备先提上游 PR，需继续推进依赖切片 | **栈式扩展（Stacked PR）** | 子切片从当前特性分支 `HEAD` 切 worktree，通过后提 PR 且 base 指向父分支；父 PR 合入后将子 PR retarget 到主干并 rebase，用 `git patch-id` 核验原审查结论是否继续有效 |
| 改动集中于少量强耦合文件，或拆不出独立用户路径 | **单 Owner 直做（Single Owner）** | 不强拆多 worktree，直接在当前 worktree 完成实现；只将只读调研与最终跨模型对抗审查派给外部模型 |

在分支内回流模式下，未提交的工作区改动不会自动进入新切出的子 worktree，因此**先建立 checkpoint commit 再扇出**是硬前提。

## 模型路由与排序

具体模型名不写死在本规范中。总控在派发前先读取本机模型配置（Cursor `~/.cursor/rules/pstack-models.mdc`、Claude Code `~/.claude/rules/pstack-models.md`、其他客户端 `~/.agents/pstack-models.md`）并核对当前运行时实际可用的模型列表。未确认可用的模型名不传入；配置缺失或模型被拒时按同角色顺位降级并如实说明。

### 角色能力分层

按认知负荷而非前后端标签分层，参考 pstack 的执行型与判断型二分法，在全局预算档位上同家族内调档：

| 角色 | 能力倾向 | 推理强度与速度 |
| --- | --- | --- |
| 总控（拆解、初审、仲裁、集成） | 当前主会话模型 | 保持上下文干净，不背重实现 |
| 只读调研 / 影响面摸底 | 快速探索模型 | 并行扇出多视角；汇总交判断型模型或主控 |
| 架构选型 / 跨模块契约 | 多模型并行面板 | 至少两个不同家族各出结构迥异的方案再综合 |
| 高难度切片（并发事务、核心状态机、安全关键路径、复杂算法） | 最强判断力模型 | 基准档位 `+1`（上限 `max`），标准速度 |
| 常规垂直切片 / 重构 / 缺陷修复 | 主力执行编码模型 | 基准档位，默认标准速度；仅主干/CI 阻塞或人工等待时启用快速档 |
| 机械迁移 / 样板 / 批量测试补齐 | 高性价比快速模型 | 基准档位降 `1~2` 档 |
| 文档 / RFC / PR 说明 | 判断与表达型模型 | 基准档位 `-1` 档 |
| 独立验证（不写业务代码，按精确 SHA 跑回归） | 独立快速验证模型 | 固定高验证档位，作者不兼任验证者 |

### 跨家族对抗审查池

按模型前缀区分家族（例如 `claude-*`、`gpt-*`、`grok-*`、`gemini-*` 互为独立家族）。有序候选池以本机模型配置的 `interrogate reviewers` 为首，并用 `arena cross-judge pool` 按家族去重依次补位。对抗审查从该有序候选池中按优先级挑选，严格执行跨家族剔除：

1. 先剔除**实现者所属家族**；若总控在初审阶段实质改写了核心逻辑，一并剔除总控家族。
2. 按切片风险等级，从剩余有序池中自前向后取席位：

| 风险等级 | 典型变更 | 对抗审查席位 |
| --- | --- | --- |
| `Low` | 纯文案、无逻辑配置微调、注释整理 | 0 席，总控初审即可放行 |
| `Medium` | 常规功能切片、标准接口与页面、一般重构 | 剩余池 **Top 1** 异构模型 |
| `High` | 权限与安全边界、数据删除、表结构迁移、核心状态机、资金与计费 | 剩余池 **Top 2 不同家族**并行对抗审查 |

### 故障重试路由

子任务失败按根因决定重试策略，最多重试两次，仍失败则停止盲试并重规划或上报：

- 上下文或内存超限：缩小切片范围，原模型重试。
- 网络断开或会话中断：保持原任务包，原模型重试。
- 工具调用异常或模型被拒：切换同角色下一顺位模型，严禁静默切回实现者同家族充当审查者。

## 双层审查与收敛

子任务交付包必须包含分支或提交范围、改动摘要、实际执行的检查命令与输出、未验证项。

### 第一层：总控初审

进入对抗审查前，由总控过滤明显问题：

1. 核对 diff 是否越界修改非授权文件、是否破坏共享契约、有无临时文件或敏感信息。
2. 核实静态检查与单切片真实行为验证已执行并通过，不采信口头宣称。
3. 横向排查多切片隐性冲突（重复定义、迁移序号、配置键、公共导出）。

初审分流：几行以内的低风险小修由总控直接处理，不开新子任务；偏题或核心缺陷直接打回，不消耗对抗审查。

### 第二层：跨模型对抗审查

1. **全新无偏上下文。** 每次对抗审查与修复后复审，都新起独立审查子任务，不继承实现者会话，也不向旧审查线程追发消息去说服对方。
2. **去偏输入。** 只提供用户目标、共享契约、精确 diff 范围与验证输出，不附实现者的自辩过程。
3. **实证门槛。** 审查者默认持红队视角，重点攻防正确性与极端边界、权限与数据安全、兼容性与迁移风险、测试是否过度 mock。沿用 [standard-dev-workflow](../standard-dev-workflow/SKILL.md) 的反馈分级：
   - `[Blocker]`、`[Major]` 必须给出 `文件:行号` 及可复现的命令、测试或反例输出；没有运行实证的臆测或风格偏好降级为 `[Minor]` / `[Nit]`，不阻塞合入。
4. **仲裁与 2 轮熔断。** 总控逐条核验 findings，剔除假阳性并附实证依据；确认的 `[Blocker]` / `[Major]` 修复后，新起干净复审任务核验未引入回归。对抗审查最多 **2 轮**；第 2 轮后仍存在未达成共识的 `[Blocker]` / `[Major]`，停止自动拉扯，整理双方实证与建议交由人裁决。

## 整体闭环与合入门禁

单个子任务各自通过不等于整体流程正常。最终合入或提 PR 前必须同时满足：

1. **端到端主流程验证。** 所有垂直切片回流或集成后，从真实用户或调用方入口走通跨切片主流程，证据要求按 [standard-quality-gates](../standard-quality-gates/SKILL.md)。
2. **审查与 CI 全绿。** 无未解决的 `[Blocker]` / `[Major]`，CI 必需检查全部通过且无冲突。
3. **提交绑定。** 审查与验证结论绑定当前待合入 `HEAD`。仅因同步基线发生 rebase 时，比对 `git patch-id`：补丁未变可沿用行为结论并补齐新 `HEAD` 的 CI；补丁有变化则重新验证受影响范围。
