---


适用前提：

- 一个用户账号可能同时属于多个租户（组织/工作空间/团队，本篇统一称「租户」），需要按
  **当前操作的租户**隔离数据可见范围
- **本篇不预设会话机制**——cookie session 或 token 都能承载租户上下文，规则与用哪种认证
  方式无关；认证/会话机制本身不在本篇范围，见 `standard-api-security-baseline`

不适用：单租户系统（一个账号只服务一个身份，没有"切换到另一个组织"这个概念）。

## 核心红线：每条查询都要带租户过滤，不能只在入口检查一次

多租户系统最危险的错误不是"没做租户校验"，而是**入口做了、查询本身没做**：

```python
# ❌ 入口验证了用户属于当前租户，但查询本身没有租户过滤
async def get_task(tenant: TenantContext, task_id: str):
    task = await task_repo.get_by_id(task_id)   # 没有 filter(tenant_id=tenant.id)
    # task_id 换成另一个租户内部的 ID 也能查到——入口检查形同虚设
```

入口的租户成员校验只证明"当前用户属于当前请求声明的租户"，**不证明请求体/路径里其他资源
ID 也属于这个租户**。跨租户越权几乎全部出在这条缝隙里。

```python
# ✅ 过滤条件下沉到查询本身，作为方法签名的强制参数
async def get_by_id(self, task_id: str, tenant_id: str) -> Task | None:
    return await db.query(Task).filter_by(id=task_id, tenant_id=tenant_id).first()
```

**查询 / 更新 / 软删除三类操作都要挂租户过滤，且没有全局默认兜底**——每个新方法都要重复写
这一行。这是刻意的：显式重复比"以为有默认过滤"更可靠，指望某个全局中间件兜底，会在新写的
批量接口、导出接口上失效（见下文「批量接口漏过滤」）。

单租户系统里"每条查询都按 `user_id` 过滤"是同一条规则的特例——把 `tenant_id` 换成
`user_id`，逻辑完全一致（单租户下的做法见 `standard-api-security-baseline` 的
`OwnerScope`）。多租户只是多了一层过滤维度，不是另一套逻辑。

## 租户上下文传递：三种方式的攻击面取舍

| 方式 | 机制 | 能被客户端篡改 | 适合场景 |
|---|---|---|---|
| **请求头声明** | 客户端在每次请求里显式声明"我现在操作哪个租户" | 是——必须配合成员校验 | 前端要频繁切租户查询、不想每次都重新登录 |
| **会话内绑定** | 登录/切换租户时把当前租户 ID 写入服务端签发的会话，后续请求从会话读 | 否——会话由服务端签名/控制，客户端改不了值 | 一次登录会话对应一个租户上下文，切换需要专门动作 |
| **路径参数** | URL 里带租户 ID，如 `/tenants/{tenant_id}/resources` | 是——同请求头一样需要成员校验 | 直观、可加书签、可分享给同租户内其他成员 |

**请求头和路径参数的值都是客户端自己声明的，不能直接信任**——必须配合"验证当前用户确实是
该租户成员"这一步，否则等于用户自己说了算，形同虚设：

```python
async def get_tenant_context(
    tenant_id: str,                                   # 来自请求头或路径，客户端可控
    current_user: TokenPayload,
) -> TenantContext:
    membership = await membership_repo.get(tenant_id, current_user.user_id)
    if membership is None:
        raise TenantAccessDeniedException()           # 不是成员，直接拒绝
    return TenantContext(tenant_id=tenant_id, user_id=current_user.user_id, role=membership.role)
```

**会话内绑定不需要每次校验成员关系**（切换租户时校验一次，写入会话即可），但需要一个专门
的"切换租户"动作去更新会话——不能指望用户改个请求头就切换成功，那样又退化成请求头方案。

三种方式不互斥：常见做法是登录时用会话内绑定确定默认租户，同时允许通过请求头临时声明另一个
（已加入的）租户去查询，两条路径都过成员校验。

## 角色权限校验：在租户上下文之后，业务逻辑之前

角色/权限校验（如"要求管理员"）依赖租户上下文，而不是替代它：

```python
async def require_tenant_admin(
    ctx: Annotated[TenantContext, Depends(get_tenant_context)],
) -> TenantContext:
    if ctx.role != TenantRole.ADMIN.value:
        raise TenantAdminRequiredException()
    return ctx
```

先解析出"这个用户在这个租户里是什么角色"（租户上下文），再判断"这个角色够不够权限"（角色
校验）——顺序不能反。角色是**租户内**的概念，脱离租户上下文单独判断角色没有意义：同一用户
在租户 A 是管理员，在租户 B 可能只是普通成员，角色校验必须先锚定"在哪个租户"。

## 跨租户越权的三种典型形态

**① 改 id 越权。** 请求头/路径带的租户标识保持自己有权限的那个不变，把请求体或路径里的
**其他资源 ID** 换成属于别的租户的 ID。如果 repository 层查询不按租户过滤，直接查到别的
租户数据——这是本篇核心红线要挡的攻击面，见上文。

**② 批量接口漏过滤。** 单条查询/更新接口写的时候容易记得加租户过滤，但**批量导出、批量
更新、后台统计**这类新写的接口，尤其是直接拼 SQL 或用 ORM 的批量方法时，很容易漏掉这一层：

```python
# ❌ 批量导出接口，忘了租户过滤，导出的是全租户数据
async def export_all_tasks() -> list[Task]:
    return await db.query(Task).all()
```

批量接口的特点是**一旦漏过滤，泄露的数据量是单条接口的成百上千倍**，且往往是导出类接口，
泄露直接体现为一份下载文件，审计更难发现。新增任何批量/导出/统计接口，租户过滤要作为
**必查项**而不是"应该记得加"。

**③ 后台管理接口绕过租户维度。** 运营后台本身需要跨租户查看/管理数据（这是合理需求），
但如果代码库里"无租户限制的查询方法"和"业务侧必须带租户限制的查询方法"没有严格分离——比如
两者共用同一个 repository 方法，只是调用方"记得"要不要传 `tenant_id`——业务侧的接口一旦
误用了后台专用的无限制版本，就等于给普通用户开了跨租户查询的后门。

✅ 无租户限制的查询方法**命名上要显眼地区分**（如显式带 `_admin` / `_cross_tenant` 后缀），
且只允许被后台专用的 use case 调用，业务侧代码审查时看到这类方法名要能立刻警觉
❌ 用一个可选参数 `tenant_id: str | None = None` 控制"要不要过滤"——可选参数默认值最容易在
新调用点被无意漏传，等于把"是否隔离"这个安全开关做成了一个容易忘记拨的选项
