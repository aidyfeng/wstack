适用前提（不满足则部分条目不成立）：

- 前端用 React Flow（`@xyflow/react`）做画布
- 后端把整张图存进单个 JSONB 列，草稿与发布快照分两张表
- 「编辑」与「执行」是分离的两个阶段——编辑产出图，引擎消费图

**本规范只管编辑侧**（建图/存图/校验/发布），不管执行引擎——那部分因项目而异（LangGraph、
自研装配器、状态机……），无法通用。

先从项目地图确认图结构、草稿／快照存储、节点注册链、执行入口与版本契约。
下面的节点名、表结构和阈值是适用前提内的设计约定；已有项目若采用不同终止方式或
并发控制，先读其偏离记录与存量数据约束，不自动迁移。新增节点的实际修改清单由当前项目提供。

本篇多数条目防的是**静默失败**：编译器不报、测试不红、线上不告警，草稿照样存得进去，只是
执行时悄悄跳过、或数据悄悄被覆盖。凡标了「静默」的地方都不能指望"出问题会有人发现"，只能
靠写的时候就不犯。

## 图数据模型：最先固定，后补代价最大

顶层结构固定为**扁平节点列表 + 显式边列表 + 入口标识**：

```
WorkflowDef = nodes[]（扁平，节点自由摆放）
            + edges[]（显式连线，source/target/source_handle）
            + start_node_id
            + 元数据
```

**不要靠数组相邻关系隐含连线。** 早期版本常见的做法是"节点按顺序排成数组，第 i 个流向第
i+1 个"——它在只有直线流程时够用，一旦要加分支、并行、循环就必须整体重构，而此时存量数据
已经是旧格式了。一开始就上 nodes+edges，即使当前只有直线流程。

**必须有显式的 start 节点和 end 节点**，两者都是真实节点，不能靠约定隐含：

- `start`：唯一，无入边
- `end`：终止节点，无出边。每条路径都要连到它

❌ **不要用"哨兵值"代替终止节点**——即让边的 `target` 指向一个保留字符串（`"__end__"` 之类），
引擎遇到即停。理由：

- **哨兵值是一条前后端各存一份、同值不同源的隐式契约**，正是下方「前后端共享常量」列为隐患
  的那类东西。终止节点走的是正常的节点类型机制，压根不需要这个常量
- **图数据模型无特例**：所有边的 `target` 都指向真实存在的节点。反序列化、遍历、可视化各少
  一个"这个 target 不是节点 id"的分支，而这类特例分支正是坏数据和渲染错乱的来源
- **可达性校验能直接套标准图算法**（从 start 能否到达 end），不必为哨兵单独写一套判断
- **终止节点身上能挂配置**——返回值、结束原因、收尾动作。哨兵值挂不了，一旦将来需要就得
  整体改回节点
- 至于"让『到此结束』在画布上成为一条可见的连线"——连到 end 节点同样是一条可见的边，
  这个好处哨兵值并不独占

**结构约束**（发布前必须全部通过）：

| 约束 | 说明 |
|---|---|
| start 唯一且无入边 | 多入口 = 执行起点不确定 |
| end 可达 | 每条路径都要能走到 end 节点，否则运行时挂起 |
| 边的 target 必须是节点 | 不存在指向保留字符串的"哨兵边" |
| 节点 id / 边 id 分别唯一 | |
| 边的 source/target 必须引用存在的节点 | 悬空边 |
| 不允许自环 | |
| 不允许孤立节点 | 运营拖进来忘了连——静默不执行，最难发现的一类错 |
| 分支节点每个出口恰好一条出边 | 条件/意图类节点的每个 `source_handle` 都要有归属 |
| 节点数 / 边数 / id 长度上限 | 防御性，也防止画布卡死 |

## 草稿与发布：双表，不是一个 status 字段

```
草稿表        整张图的当前编辑态，编辑/保存/发布校验读它
发布快照表    发布那一刻的完整副本，执行读它
```

**执行只读发布快照，绝不读草稿表。** 否则运营编辑到一半（图还没连完）就会影响正在运行的
线上流程——这是最容易被"反正加个 status 字段判断一下就行"糊弄过去的地方，但 status 挡不住
"已发布过、现在又在改"这个状态。

**发布流程**（顺序不能变）：

1. 跑发布门校验，不通过直接拒绝
2. 草稿状态置为已发布
3. 旧发布快照**软删**（保留 `deleted_at`，不物理删——要能回溯线上跑的是哪一版）
4. 写入新的完整快照

**调试/预览读草稿**——这是刻意的不对称：运营要能在发布前试跑当前编辑态。

状态枚举保持最小：`DRAFT`（未发布，或发布后又编辑过）/ `PUBLISHED`。

## 两道校验门：早晚分开

新增校验规则前先判断它属于哪一层。放错层的后果是双向的：**该早的放晚了 → 坏结构混进发布；
该晚的放早了 → 运营存不了中间态草稿。**

| | 结构完整性校验 | 业务/发布语义校验 |
|---|---|---|
| 管什么 | type 是否合法、字段类型是否吻合、边引用是否存在、id 是否唯一、handle 是否合法 | 环检测、可达性、分支是否穷尽、领域规则（如"这类节点后面不能接那类"） |
| 何时拦 | **每次保存**（含自动保存）都跑 | **只在发布**时跑 |
| 判据 | "这个值的类型/形状对不对" | "这张图能不能安全上线" |

结构校验必须在反序列化时**严格失败、不静默兜底**：未知节点 type → 抛错；缺必填/多余字段 →
抛错。静默兜底会让坏数据一路存进 DB，等到执行时才炸，且那时已经查不出是谁写进去的。

业务校验的规则建议编号（`V1`、`V2`……）并在报错里带上编号，运营反馈问题时能直接定位是哪条
规则拦的。

## 前端画布（React Flow）

**`nodeTypes` 注册表必须是模块级稳定引用。** 在组件内联定义会让 React Flow 每次渲染都认为
节点类型变了，触发全量重挂载。

```ts
// ✅ 模块级常量
export const workflowNodeTypes = { clip: ClipNodeCard, condition: ConditionNodeCard, ... }

// ❌ 组件内定义 —— 每次渲染都是新对象
function Editor() { const nodeTypes = { ... } }
```

**节点组件按 Handle 模式分类，不是按业务类型一一对应：**

- **固定 handle**（一进一出）的多种节点 → **合并成一个组件**，按 type 切换图标/配色
- **动态 handle**（分支数由配置决定，如条件节点每个分支一个出口）→ **各自独立组件**

按业务类型一对一拆组件会产出大量近乎重复的卡片代码。

**三种加节点方式**，缺一都会让运营别扭：

| 方式 | 触发点 |
|---|---|
| 在节点后追加 | 节点上的 `+` 按钮 |
| 在边中间插入 | 边上的 `+` 按钮（自动重连前后） |
| 放到视口中心 | 工具栏/类型选择器 |

**属性面板按 type 分发 + patch 局部更新。** 每类节点的表单各自持有一个
`patch(partial: Partial<XxxNode>)` 闭包，只合并变化字段：

```ts
function patch(partial: Partial<ClipNode>) {
  onChange((n) => ({ ...n, ...partial }))
}
```

❌ 不要整节点重建后回写——会把并发的其它字段改动覆盖掉。

面板组织有两种形态，规模决定选哪种：类型少时单文件按 type 分支渲染；类型多、每类表单都复杂
时拆独立面板组件。**同一项目内保持一致**，不要一半一半。

**撤销/重做用快照式，不用指令式：**

```ts
{ past: Snapshot[], present: Snapshot, future: Snapshot[] }
// Snapshot = { nodes, edges }
```

- 深克隆存快照，防引用共享导致"撤销了但对象还是同一个"
- 相邻快照做内容比较去重（`JSON.stringify` 足够），避免拖动过程中产生几十个无差别快照
- 深度上限（50 层左右），否则大图会吃内存
- 快捷键要与浏览器默认行为区分，且见下方「多实例串台」

指令式（记录每步操作 + 反操作）在图编辑场景收益很低：操作种类多、每种都要写反操作，
而快照的内存代价在图规模下完全可接受。

**自动保存：debounce 3 秒左右**，变更停止后触发。`isDirty` 靠**当前图与服务端图做内容比较**
得出，不要用"有没有触发过 onChange"——后者在拖动节点后又拖回原位时会误报。

**并发编辑必须有乐观锁。** 保存时带上取图时的 `updated_at`，服务端比对不一致就返回专门的
冲突错误码，前端提示"这张图已被他人修改"。没有这层，两个人同开一张图就是**静默互相覆盖**，
且后保存的人完全无感知。

**图数据双向转换集中在一个模块**：`graphToFlow(graph)`（加载）/ `flowToGraph(nodes, edges)`
（保存）。React Flow 的节点结构（`position`、`data` 嵌套）与后端存储结构不同，转换逻辑散落
到各处会导致两边字段慢慢对不上。

## 扩展一种新节点类型：全链路清单

这是本类系统最容易出错的操作——**漏改一处通常不报错，只是静默失效**（草稿存得进去，执行时
跳过，或画布点开没有属性面板）。改之前先按项目实际情况把清单列全，逐项打勾。

后端：

1. **类型定义** —— 新增节点的数据类，并加入节点联合类型
2. **序列化/反序列化分支** —— to_dict / from_dict 两个方向都要加判别分支
3. **校验分派** —— 结构校验的类型分派链加一支；若项目有"语义分组"（如"屏幕类节点"
   "产出内容类节点"驱动某些发布规则），必须把新类型并入对应分组，**漏并入会让新类型悄悄绕过
   那些规则**
4. **执行分派** —— 引擎遍历时的类型分派链加一支

前端：

5. **TS 类型联合** —— 新增 interface 并加入判别联合
6. **画布注册表** —— `nodeTypes` 加一行，key 与后端 type 判别值同名
7. **卡片组件 + 属性面板分支** —— 注意属性面板若有"无匹配时的兜底分支"，别让新类型漏判进兜底

跨端：

8. **评估客户端契约版本号是否要 +1**（见下节）

## 反序列化健壮性：全库扫描必须逐行兜底

图反序列化会因存量脏数据抛错。**一条历史坏图会让全库范围的统计/引用分析整体崩溃**，波及与
那条坏图毫无关系的操作——运营发布 A，却因为库里另一条无关的 B 坏了而失败，且报错信息不指向 B。

两种调用场景，处置相反：

```python
# ✅ 当前正在操作的这一行 —— 严格，转成带上下文的领域异常抛出
try:
    definition = record.to_def()
except (ValueError, KeyError, TypeError) as e:
    raise InvalidWorkflowPayload(f"图结构非法:{e}") from e

# ✅ 遍历全部已发布图 —— 逐行兜底跳过，不让异常冒泡
for r in records:
    try:
        defs[r.id] = r.to_def()
    except (ValueError, KeyError, TypeError):
        logger.warning("skip_broken_graph", flow_id=r.id)   # ★ 必须记日志
        continue
```

**兜底必须记日志。** 静默 `continue` 会让"受影响范围分析"少算——本该被判定为受影响的图因为
解析失败被跳过，界面显示"无影响"，运营据此发布，然后炸。

## 前后端共享常量：同值不同源就是隐患

handle 名、节点 type 判别值等常量往往前后端各定义一份、没有共享类型文件。改一处不改另一处
的后果是渲染错乱或执行走偏，且**测试通常测不到**（前后端各自的测试都用自己那份常量）。

- **首选是让这类常量根本不存在**：凡是能用真实节点、正常类型机制表达的，就不要发明保留
  字符串——上面禁用终止哨兵正是这条原则的一个应用
- 消除不掉的（如 handle 名），建立时就在两侧注释里互相指认对方位置
- 改值前先确认存量数据——这些字符串已经写死在历史图的 JSONB 里，改值等于让所有历史数据失效
- 能生成共享类型/常量文件就生成（OpenAPI codegen 等），不能就靠纪律 + 注释

## 客户端契约版本号

若图（或图的裁剪子集）会下发给客户端渲染，需要一个**形状契约版本号**，让客户端判断自己认不
认识这份数据。

要点是划清它**不是**什么：

- 不是图存储格式的版本号（那由结构校验保证）
- 不是某条图的草稿/发布版本号（那是每次编辑 +1 的业务版本）

何时 +1：新增节点 type、或对既有节点做**破坏性**字段变更（改变已有字段形状）。
何时不 +1：只加字段、不动既有字段——老客户端忽略不认识的字段即可。

漏 bump 的后果：老客户端拿到不认识的 type，要么崩溃要么静默丢内容，且**没有任何信号**提示
这是一次不兼容变更。

## 共享子图的参数归属

支持"子图被多处引用"时，**随调用场景变化的参数归调用方节点，不归被引用的子图内部**。

典型的是那些随场景伸缩的配置（时长档位、音量、间隔）。把它们焊死在共享子图内部节点上，
另一个引用方的场景键对不上，解析时会**静默退回默认值**——行为漂了却不报错。

推论：**引用节点上的覆盖类参数，默认值必须是"不覆盖"（`None`），不能照抄普通节点的具体默认值。**

```python
# ❌ 照抄普通节点的默认值 → 全库存量引用点的行为被静默改写
pad_ms: int = 200

# ✅ None = 不覆盖，语义与"这个字段本来不存在"完全一致
pad_ms: int | None = None
```

这是"新增字段的默认值必须不改变既有行为"这条通则在本场景的具体形态。
